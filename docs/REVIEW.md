## 1. Cortex-M 时钟参数检查（采纳）

`hal/cortex_m.zig` 的检查是 `if (cpu_hz < 1000)`，而错误信息和注释都写着要求 1 MHz。
评审指出 `cpu_hz = 1000` 会被放行。**确认属实。**

后果比"reload 为 0"更严重，值得写清楚：SysTick 的 reload 为 0 时计数器**不会重装**，
于是中断再也不来，`now()` 永远停在 0，所有 `wait_ms` 永久挂起。不是时钟不准，是死机。

已改为 `< 1_000_000`，并把后果写进错误信息。同时补了一处评审没提的问题：
原先 `reload > 0xFFFFFF` 时**静默钳位**，这会悄悄产生一个谁也没要求的周期；
现在改成编译期报错。

另外修正了 `reloadValue()` 的文档——它写的是"CPU frequency"，实际返回 reload 值。

**验证**：用一个故意写错的探针文件编译，确认两种错误都真的触发：

```
src\hal\cortex_m.zig:88: error: cpu_hz must be at least 1 MHz for a 1 ms SysTick;
got 1000 Hz. The reload is cpu_hz / 1000 - 1, which reaches zero below 1 MHz...
```

## 2. 事件标志的 volatile 纪律（采纳）

`kernel/shared.zig` 明确规定 ISR 共享状态必须走 volatile 访问，而 `kernel/events.zig`
直接读写 `self.bits`。**确认属实，且这确实是自相矛盾。**

危害是具体的：编译器看不到 ISR 这个"写者"，因此有权把 `bits` 的读取提升到循环外。
下面这种写法可能被编译成死循环：

```zig
while (!flags.isSet(EVT_LINK_UP)) {}   // 可能再也不重新读 bits
```

已把 `bits` 的**全部**读写改走 `shared.load/store`。注意读也要 volatile——这是关键，
只改写是不够的。

新增测试直接复现该模式（循环内写入，断言迭代次数），并补了一条"清除一个标志不会
误伤同一轮里到达的另一个标志"。

**代价已实测**。在 Smartcar-Template 的 cyt2bl3 整机上做 A/B（其他条件完全相同，
只换内核）：

| | `.text..Luser.zig_loop` | `.bss..L_MergedGlobals` | 整机 flash |
|---|---|---|---|
| 改前 | 336 | 76 | 154 400 |
| 改后 | 408 | 104 | 154 472 |

+72 B flash、+28 B RAM（0.046% / 0.2%）。逐文件二分确认**全部来自 `events.zig`**，
且进一步用"只把 `snapshot()` 的一行改成 volatile 读"复现了同样的 +72/+28——
所以这是 volatile 语义本身的代价，不是写法问题：volatile 访问会抑制 LLVM 跨整个
内联函数的若干内存优化。

判断是**接受**：换来的是一条不会被人忘记的纪律，代价是万分之五的 flash。

**同一类问题在 `chan.zig` 里也存在，评审没有看到**：`head` 走了 `shared`，但 `tail`
没有。`tail` 由消费者（任务）写、由生产者（ISR）读，因此同样是双向共享状态，
`pushFromIsr` 直接读 `self.tail` 会被编译器缓存——一个一直读到陈旧 `tail` 的生产者
会**永远报告"满"**。已一并修正，见 §8。

## 3. RISC-V 定时器参数（采纳，且问题更大）

评审指出 `period = cfg.timer_hz / 1000` 在 `timer_hz < 1000` 时为 0，会让定时器
持续触发。**确认属实。**

但真正的问题在**默认配置**上：`Config.timer_hz` 默认是 `32_768`。

```
32768 / 1000 = 32        // 每"毫秒"只有 32 个周期
32 / 32768 = 0.9766 ms   // 实际周期
```

**时钟快 2.34%，每小时累积 84 秒。** 这比晶振误差大两个数量级，会让时间戳和 PID
时序明显跑偏。评审把它归为"需明确非整数毫秒频率如何换算"——照做的话只会得到一句
注释，而正确做法是把它算对。

`mtimecmp` 是**一次性**比较器，每次 tick 都可以换周期，所以不需要像 SysTick 那样
忍受固定周期。新增 `kernel/tick.zig` 的 `MillisecondGrid`，用 Bresenham 误差扩散
在 32 与 33 之间交替，使**平均值精确等于 1 ms**：每 1000 tick 恰好消耗 32768 个周期。

放在 `tick.zig` 而不是 `riscv.zig` 是有意的——它是纯整数运算、与架构无关，
因此可以在主机上测试。`riscv.zig` 只是使用者。

`configure()` 改成接受 `comptime` 参数，把非法频率变成编译错误：

```
error: timer_hz must be at least 1000 Hz, got 999. A 1 ms period is
timer_hz / 1000 cycles, which is zero below that...
```

**验证**：数值测试断言 1000 次 tick 恰好消耗 32768 周期、其中 768 次是长周期、
232 次是短周期；并断言 `next()` 永不返回 0。两个编译期守卫都用探针确认会触发。

## 4. RT1064 目标检查（部分驳回）

评审称 README 声称验证了 RT1064，但 `build.zig` 的目标列表里没有它，只有
CYT2BL3、CYT4BB7 CM0+、CYT4BB7 CM7。

**覆盖是存在的。** RT1064 与 CYT4BB7 的 CM7 核三元组完全相同：

| | 三元组 |
|---|---|
| `templates/base/rt1064/Makefile` | `thumb-freestanding-eabihf` + `cortex_m7+fp_armv8d16sp` |
| `templates/base/cyt4bb7/Makefile`（CM7 分支） | `thumb-freestanding-eabihf` + `cortex_m7+fp_armv8d16sp` |

所以 `smartcar_cyt4bb7_cm7` 这个条目**已经**在编译 RT1064 的目标配置。评审把它读成
"RT1064 没有验证"，是因为列表里没有一个叫 rt1064 的条目。

但评审的**底层关切是成立的**：一个只能靠读者自己发现"两块板恰好同三元组"才能核实
的说法，等于无法审阅。所以处理方式是加一个显式的 `smartcar_rt1064` 条目
（代价是多编译一个目标），并把注释改成说明这件事。现在 `check-targets` 的输出里
能直接看到 RT1064。

README 也补了一张目标名 ↔ 芯片的对应表，并明确"交叉编译验证 ≠ 真机验证"。

## 5. `*anyopaque` 与类型安全（驳回）

评审建议评估"是否能通过生成专用 task table 保留更多静态类型信息"。

**运行时开销是零，类型安全也已经是编译期强制的。** 两条证据：

**（一）`poll` 函数根本不存在。** 编译 cyt2bl3 的 Zig 对象后检查符号表，
77 个具名符号里没有任何 `poll` 函数——只有模块状态变量：

```
app.blink_state.0
app.status_state.3
app.telemetry_state.0
```

`Scheduler.run()` 用的是 `inline for (defs, 0..)`，`def` 是 comptime 已知的，
`def.poll` 因此是常量函数指针，被 LLVM 直接内联。既然函数没被生成，就不存在
"取地址"这回事，也就无从间接调用。

**（二）重定位表里没有任何 poll 相关项。** 唯一指向代码的调用重定位是
`coremark_run_once`（`R_ARM_THM_CALL`），是直接调用。

至于类型安全：`App` 在编译期校验每个实例的 `state` 必须是 `*Module.State`
（`validateModule`），而 `makePoll` 里的转换正是由这条校验保证的。转换点安全，
且检查发生在编译期。

换句话说，`TaskDef` 用 `*anyopaque` 是**为了让异构的模块实例能放进同一个数组**，
而不是放弃了类型信息。手写任务表的形式（`Scheduler(Hal, .{...})` 直接传元组字面量）
连这一步都不需要，每个任务的 `ctx` 保持具体类型。

真要做"专用 task table"，需要用 comptime 构造异构元组类型，复杂度上升、
可读性下降，换来的是一个已经为零的开销。**不做。**

## 6. Topic 序列化（一半已实现）

评审给了五条建议。其中"强制要求 extern struct"**从第一版起就已实现**：

```zig
if (info.layout != .@"extern") {
    @compileError("Topic '" ++ name ++ "' payload must be an `extern struct`...");
}
```

其余四条已补上，都是编译期检查：

| 检查 | 拒绝的情况 |
|---|---|
| 端序 | 大端目标（原始字节拷贝只在 LE 上等于线格式） |
| 字段宽度 | `usize` / `isize`（宽度随指针大小变，RV32 与 RV64 帧不同） |
| 指针字段 | 对主机解析器无意义，宽度也不固定 |
| **padding** | 有隐式填充的结构体 |

最后一条是这批检查里最有价值的，评审只写了"对齐、padding 的静态断言"。隐式 padding
的字节会被 `@memcpy` 复制进帧，但 Zig 不保证初始化它们，于是**同一个值可以序列化成
不同的字节**。帧自己的 CRC 覆盖的是实际发出的内容，所以接收端**无法发现**。
这是静默的非确定性，必须编译期拒绝。

现在会给出可操作的报错：

```
error: Topic 'padded' payload has 3 byte(s) of padding (5 bytes of fields,
8 bytes of struct). Padding is copied into the frame but is never initialised,
so the same value can serialise to different bytes. Reorder the fields, or add
explicitly named padding fields so the bytes are deterministic.
```

**验证**：四个守卫逐个用探针确认触发，其中大端那条是真的用
`powerpc-freestanding-eabi` 目标编译验证的；同时确认合法载荷（`f32×3`、
显式 pad 字段）仍被接受。

"与真实 LibXR 逐字节 golden test"**未做**，原因见 §8——它需要 LibXR 源码，
而当前实现的多项式本来就标注为待核对。

## 7. CI 与文档一致性（采纳）

仓库里确实没有 `.github/workflows/`。已添加，并**固定 Zig 版本**（`.zigversion` +
workflow 里读取），因为 Breeze 依赖不少 Zig 的 comptime 行为，未固定的工具链会把
一次例行 runner 升级变成无法解释的红灯。

workflow 里加了一步断言：`check-targets` 必须编译出恰好 7 个对象。目标列表是 README
的对外声明，静默变短必须失败。

同时修掉文档与实现的漂移（评审只发现了 RT1064 那处，实际漂移范围更大）：

| 位置 | 原文 | 实际 |
|---|---|---|
| README | 59 个单元测试 | 75 |
| README | 6 个目标 | 7 |
| ARCHITECTURE.md（两处） | 59 个单元测试 / 6 个目标 | 同上 |
| FUSION.md（两处） | 59/59 单元测试、6 个目标 | 同上 |

**处理方式不是把数字改对，而是不再重复它们**：README 的状态行是唯一来源，
ARCHITECTURE.md 与 FUSION.md 改为引用 README。然后 CI 增加两步，
把 README 声称的数字与实际解析出的数字比对——写在这里的数字现在会**编译失败**，
而不是悄悄过期。这是"文档漂移"这类问题的唯一可靠解法。

## 8. 本次新发现（评审未提）

**（一）事件标志是电平触发，且永不自动清除。**

这是评审在架构建议里问到的"明确 EventFlags 是电平触发还是边沿触发"。答案是
**电平触发、不自动消费**，而且与 `Program` 的一个行为叠加后会产生反直觉的结果：

`Program.poll` 在跑完指令表后会 `reset()` 自己（`program.zig:173`），即**自动重新开始**。
于是"等待某事件 → 做一件事"的程序，只要那个标志没人清，就会**每一轮都重新执行一遍**。

这是设计选择（消费是调用者的事，`clearEvents`），对"链路已连接""帧已就绪"这类
状态语义是正确的，但必须让人看得见。已在 `events.zig` 头部明确写出两条推论，
并新增两个测试把它钉住——其中一个证明了"不清理就会每轮重复"。

**决定：语义保持不变。** 不引入自动清除，也不引入边沿语义。理由：

* 自动清除会让"两个任务关心同一个标志"变成竞态——先跑的那个把标志吃掉，
  后跑的永远看不到。电平语义下两者都能观察到，这恰恰是协作式调度想要的性质。
* 边沿语义需要计数或序列号才能不丢事件，那就不再是一个字、零分配的通道，
  而 `Channel` 已经提供了带丢弃计数的有storage版本，两者分工是清楚的。
* 代价是调用者必须记得清。这条已经写进 `events.zig` 的头部文档并有两个测试
  兜底，属于"必须显式"而不是"容易忘记"。

对应的调用约定因此固定为：**在处理完的那一轮末尾清除自己处理过的位**。

**（二）`Channel` 的 `tail` 也违反了同一条 volatile 纪律。**

评审只看了 `events.zig`，但 `chan.zig` 有同一类问题：`head` 的读写都走 `shared`，
`tail` 却直接读写。而 `tail` 是**双向共享**的——消费者写、生产者（ISR）在满判断里读。
被缓存的 `tail` 会让生产者永远认为环是满的，表现为静默丢数据。

已把 `tail` 的读写也改走 `shared`（`pushFromIsr` 读、`pop` 与 `reset` 写）。

顺带确认了评审担心的"极端 head/tail 回绕"**不适用**：两个索引始终以**掩码后的形式**
存储，范围是 `0..slots`，`head +% 1` 不可能溢出被 `mask` 限住的值。这不是巧合，
是"capacity+1 必须是 2 的幂"那条约束的副产品。新增了一个 10 万次推入的测试，
每一步都断言索引不越界。

**（三）`--gc-sections` 会吃掉无调用者的导出。** 见 FUSION.md §7.10，
`zig_worst_lateness` / `zig_grid_resyncs` 并不在最终镜像里。

**（四）Cortex-M 的静默钳位**，见 §1。

## 9. 推迟项

| 建议 | 为什么推迟 |
|---|---|
| HAL 契约拆成"必需 + 可选能力" | 合理，但要动所有后端和接线示例；当前只有 `idle` 是可选的，收益还没到 |
| 调度器执行预算 / watchdog hook | 需要先有"任务超时"的语义定义。`Program` 已有 `max_instrs_per_poll` 上限，评审这条**部分已实现** |
| 静态优先级 / 阶段分组 | 与"按声明顺序执行、时序可静态推理"的现有取舍冲突，属设计变更 |
| `Program` 步数/耗时诊断 | 步数上限已有；耗时统计需要每任务计时，会引入新的共享状态 |
| `stack_hint` 变成可验证约束 | 需要静态栈深度分析，Zig 目前没有；保持为文档字段比给虚假保证好 |
| 模糊测试 / 属性测试 | 值得做，但应针对 `Channel` 与 `topic.pack/unpack` 单独设计 |
| Topic 与真实 LibXR 的 golden test | 需要 LibXR 源码核对 CRC 多项式；已记在 FUSION.md §4.2 |
| C 算法层迁移 | 既有计划（S1 之后），与本轮评审无关 |

这个缺口本轮只是缩小，没有消除。

## 结论

评审的**方向判断是对的**——真正的短板确实在底层共享状态与 HAL 边界条件上，
而不是架构方向。三个功能性 bug（Cortex-M 阈值、事件标志可见性、RISC-V 周期）
都是真问题，其中 RISC-V 那条的实际影响比评审描述的更大。

同时有两处需要指出：RT1064 的覆盖**并非缺失**（三元组相同），
`*anyopaque` 的**运行时开销为零**且类型安全已在编译期强制。
这两条如果照单全收地"修"，会把正确的设计改坏。

暂未处理的最大一块是 **C 算法层迁移**，以及 **EventFlags 的触发语义是否要改**
——后者需要设计决策，不适合在"规整"里顺手决定。

## 11. `check-targets` 是空转的（已修）

**这是本轮最重要的发现，而且它让"7 个目标已编译验证"这句话在其中一个目标上是假的。**

Zig 对**没有下游消费者**的产物会传 `-fno-emit-bin`，编译在语义分析之后就停下。
`check-targets` 用的是 `addObject` 且没有任何步骤消费它，所以这条命令行里一直带着
`-fno-emit-bin`——**内联汇编从未被真正汇编过**。

怎么发现的：为了核对文档里的尺寸表，用文档里那条等价命令手工编译，其中 RISC-V 那条失败了：

```
error: <inline asm>:1:2: unrecognized instruction mnemonic
        msr primask, a0
```

`msr primask` 是 Cortex-M 的汇编。也就是说 RISC-V 骨架**根本构建不出来**，而
`zig build check-targets` 一直是绿的。同一件事我几天前刚在 zig-orch 上踩过
（`addObject` → 产物 516 B，里面根本没有内核），这次是同一类错误出现在 Breeze 自己身上。

修复：把每个产物安装一份（`b.addInstallFileWithDir`），强制真正产出 `.o`。
修复**有牙齿**是验证过的——把 `criticalExitRestore` 里的 `msr primask` 改成
`msr primsk`，两种模式对比：

| 命令 | 结果 |
|---|---|
| `build-obj -fno-emit-bin`（旧行为） | 静默通过 |
| `build-obj -femit-bin=…`（新行为） | `<inline asm>:1:6: invalid operand for instruction` |

顺带一个副作用：安装步骤会让 `--summary all` 在安装行下面重复打印一次 compile 行，
CI 里 `grep -c 'compile obj breeze_fw_'` 会数出 14 而不是 7。已把 grep 锚定到 `^+- `，
并在 workflow 注释里写明原因——否则下一个"顺手简化"的人会把这个检查弄坏。

## 12. `export fn` 把 Cortex-M 汇编拖进了其它目标（已修）

`hal/cortex_m.zig` 末尾有两个 `export fn`（`breeze_critical_enter_saved` /
`breeze_critical_exit_restore`），存在的理由是**让那段内联汇编无论如何都被汇编到**：
`criticalEnterSaved` / `criticalExitRestore` 内核根本不用，没有调用点，
`comptime { _ = &fn; }` 也证明无效（当时故意写坏助记符仍然编译通过）。

问题是 `export` 的语义比这强得多：**只要文件在模块图里，`export` 就会为构建该模块的
每一个目标产出**。于是 Cortex-M 的汇编被汇编进 RISC-V 构建里。修复 §11 之后，
这个副作用立刻变成硬失败。

单变量实验（在临时 worktree 里做，只改这一处）：把两个 `export` 降级为普通 `fn`，
RISC-V 骨架立刻构建成功。

修复方式不是删掉验证，而是把它挪到该在的地方：`examples/firmware_cortex_m.zig` 里加了
`halAsmCoverage()`——一个 `export fn`，显式调用那几个没有调用点的 HAL 函数。
验证从"链接决定的副作用"变成了"调用点上看得见的一行"。RISC-V 骨架加了同样的函数。

**这一条值得记住的地方是：这个装置本来是为了让检查更严，结果既没起到作用（因为 §11），
又弄坏了一个目标。** 验证手段本身也需要被验证。

## 13. `Boot` 每个 pass 重跑一遍，而且从来没有真正归拢（已修）

`firmware_smartcar.zig` 的 `Boot` 用 `wait_event_timeout(EVT_IMU_READY, 250)` 等 IMU。
两个问题叠在一起：

1. `Program` 跑完会**回到指令 0**（这是设计，周期任务靠它），而 `Boot` 没有闩锁，
   于是每次通过都重跑整个启动序列，`attempts` 无界增长；
2. 它等的标志是电平触发且**永不自动清除**的，所以第一次成功后每次通过都会"立刻满足"。

`events.zig` 的模块注释里其实**已经写明**这条规则（"A task waiting on a flag that
nobody clears will keep firing. Since `Program` restarts itself…"），是示例没有遵守
自己内核的规则。

改写为它本来就该是的东西：IMU 与 ESC **同时**上电，通过 `Join.Of` 归拢，超时不再
等一个标志，而是**把仍在 `.running` 的槽位逐个 `fail`**，然后走原有的重试分支。
这正是计数式 `Join` 表达不了的动作——它不知道该失败哪一个。

顺带修掉两处把 `period_ms = 0` 写成"事件驱动"的注释：调度器的规则是
`period == 0 or tick.reached(...)`，也就是**每个 pass 都轮到**，这也正是上面第 1 条
能发生的原因。

实测（CYT2BL3）：**1556 B flash / 364 B RAM → 1968 B / 340 B**。flash 涨了，RAM 没涨。

## 15. `Join` 的计数器是读-改-写（未改，已记录）

`Join.pending` 的 `+= 1` / `-= 1` 在 ARMv6-M 上是 load-add-store，没有
`LDREX`/`STREX` 可用。两个完成路径若能互相抢占（不同优先级的中断，或中断落在
`enter` 中间），就会丢一次更新，**join 永远不完成**。

这**不是**新引入的问题，但它此前只被含糊地写成"可从 ISR 使用"。现在：
模块注释里给了具体的失败场景，`Join` 的类型文档写明需要 HAL 临界区，
并明确指出 `Join.Of` 不存在这个问题——因为每个槽位是自己的字、每个阶段都是整值写入，
两次完成永远不碰同一块内存。这也是在中断优先级不受自己控制时应该优先用 `Join.Of` 的理由。

单元测试 `the counter hazard that Join.Of is shaped to avoid` 把这个交错过程写成了可执行的形式。

为什么不直接修：无锁的无界计数器在 ARMv6-M 上不存在，有界的方案就是 `Join.Of` 本身。

## 16. 融合示例只被编译过，从未被执行过（已解决，见 §25）

README 的开篇承诺是"同一份内核可以在主机上用虚拟时钟运行，因此固件逻辑能在工作站上被精确断言"。
内核确实如此（104 个测试）。但**融合示例不满足**：它在文件作用域绑定了
`breeze.hal.cortex_m`，因此无法在主机上 import；而 CI 对它只做交叉编译。

§13 那个 bug 就是这件事的代价：编译全绿，逻辑错了两处，靠人读出来。
一个把 `Boot` 跑一遍成功/失败/超时三条路径的主机测试会直接抓到它。

建议（未做，属结构性改动）：把模块定义与"接线"分开——模块放进不引用任何 HAL 的文件，
接线留在示例里；再补一个主机测试，用 `App.SchedulerFor(HostHal)` 驱动同一批模块。
这样"固件逻辑能在工作站上断言"对示例也成立。

## 19. 两个根文件的导出面会悄悄分叉（未修，已记录）

`tools/vendor.ps1` 交付的是 `breeze_kernel.zig`——**别的仓库真正编译的是它**，
不是 `breeze.zig`。两个文件各自手写一份内核导出清单，于是"在 `breeze.zig` 里加了类型、
忘了在内核根里加"这种漂移不会让任何东西失败，只会让 vendored 的项目少一个类型。

现状**是一致的**（逐条核对：内核根 = 全根减去 `app` 与 `hal`），但没有任何东西保证它。

加反射守卫的尝试失败了，原因本身值得记下来：Zig 0.16 的 `builtin.Type.Declaration`
**只剩 `name`**，`is_pub` 已被移除。反射因此无法区分"导出的名字"和"私有辅助函数"，
"全根里的每个导出都必须在内核根里存在"这条就表达不出来；勉强写出来会因为任何一个
私有声明而误报。宁可留一个空位，也不要留一个迟早被删掉的脆弱测试，所以没加，
只在 `breeze.zig` 的测试块里写下这件事。

可行的方向有两个：把 `breeze.zig` 的内核导出改成从内核根**派生**，彻底消灭重复；
或者让内核根自带一份清单，由 CI 比对两份。两者都还没做。

## 20. 本轮的方法

* 每条结论都给了可复现的命令或探针；**改代码之前先让检查失败一次**，确认它有牙齿。
  这一轮有两条结论正是靠"先让旧做法失败"才成立的（§11 的 `-fno-emit-bin` 对比、
  §12 的降级 `export` 单变量实验）。
* 修完的提交逐个在临时 worktree 里跑 `zig build ci`，**确认每个提交自身都能构建**
  （第一版提交顺序错了：`Boot` 用到 `Join.Of` 的提交排在引入 `Join.Of` 之前，已重排）。
* 重新 vendor 之后，把 Smartcar-Template 的 cyt2bl3 模板**重新组装并完整链接**了一遍
  （`make` 退出码 0，产出 `cyt2bl3.elf/.bin`），所以"两边同步"这次不只是哈希相等，
  而是真的编进去了。
* 仍然没有被验证的：**真机行为**。7 个目标全部只是交叉编译，没有任何一条结论来自硬件。
  这与第一部分的结论相同——这个缺口本轮同样只是缩小。

另外几条只影响"注释比代码说得更满"，一并改了：`Program.isAtStart` 的 "not mid-wait" 只覆盖

对照参考实现）、`MillisecondGrid` 的 32768 整除关系、事件快照/清除纪律、
以及 CI 的两条断言在缓存与冷缓存下都等于 README 里的值。

## 22. 两条未修项：它们是设计决定，不是 bug

### a. `setFromIsr` 的读-改-写（本轮最严重）

两个代理独立复现了同一件事：所有中断都在同一个字上置位，不同优先级的中断互相抢占时，
被抢占者写回的旧值会覆盖抢占者刚置的位——**事件永久丢失**，等在 `wait_event` 上的任务
再也不会被唤醒。源码里的理由（"ISR 是这条路径上唯一的写者"）只覆盖了任务与中断之间，
没有覆盖中断与中断之间。

显而易见的修法是在 ISR 里也屏蔽中断，但这条路在两个后端上**不对称**：

* Cortex-M 的 `criticalEnter`/`criticalExit` 是 `cpsid i`/`cpsie i`，在 ISR 里用是安全的；
* RISC-V 的对应实现是 `csrrci mstatus, 8` / `csrrsi mstatus, 8`——**`criticalExit` 是无条件
  置位 MIE 的**，在 trap handler 里调用它会当场打开中断。它的注释写明这是有意为之
  （避免多余的 `criticalExit` 破坏嵌套）。也就是说 RISC-V 后端没有可嵌套的临界区，
  而 Cortex-M 后端有一个（`criticalEnterSaved`/`criticalExitRestore`）。

要真正修好，得先让两个后端的临界区都变成"保存-恢复"语义，或者明确规定"置位标志的
中断必须同优先级"并把这条约束写进 HAL 契约。

**决定：写进契约。** 理由正是上面那条不对称——RISC-V 的 `criticalExit` 无条件置位 MIE
是有意为之（避免多余的 `criticalExit` 破坏嵌套），为了一条 ISR 路径去改它的语义，
影响面比这条约束大。而且"置位标志的中断同优先级"本来就是多数固件的默认做法。

已改：`hal.zig` 的"中断规则"一节把这条写成契约（含失败场景与"为什么不做成编译期检查"——
中断优先级在 NVIC/mip 寄存器里，是运行期事实，内核看不见）；`events.zig` 的模块注释与
`setFromIsr` 的类型文档同步改写；两个固件骨架在 ISR 段落里点名这条约束在真实工程里的位置。
注意这条**无法**由内核强制，只能靠评审与文档——这也是它被写进契约而不是被"修掉"的原因。

### b. 挂起时的 `idle`

只要有任务返回 `.pending`，它每个 pass 都算"跑过"，`Hal.idle()` 就永远不会被调用。
后果是需要等事件的任务会把循环跑成 100% 占用——对电池供电的小车是真问题，
而 FUSION.md 里"空闲不再忙等"这句话只在**没有挂起任务**时成立。

反过来说，改法本身有代价：一旦允许在"只是重新轮询挂起任务"时 `wfi`，多趟序列的推进速度
就从"每个 pass 一次"降到"每个中断一次"（tick 频率），对按位模拟的时序是数量级的变慢。
所以这是"功耗 vs 挂起任务的推进速率"的取舍，不是对错。

**决定：保留任务的推进速率。** 也就是说这是个**有意保留的行为**，不是待修的缺陷。
需要边等边睡的写法是：让中断去等，任务直接返回 `.finished`。

已改：`hal.zig` 的 `idle` 契约写明"没有任务到期的整趟才调用 `idle`"以及挂起任务会
让循环保持清醒的原因；`FUSION.md` §7.5 里"空闲不再忙等"那句话补上了边界条件与这次取舍。

## 26. 把 C 算法层整体修好，并给它加一道门（已实施）

**修了什么**

|---|---|---|
| `BreezeCommBuffer` 被完整定义两遍 | 1 处 | 两处都是**匿名**结构体，在 C 里是两个不同类型，于是同时包含就冲突。`comm_buffer.h` 改为包含 `comm_interface.h`，只留一个定义点 |

* **预期来自语料而不是写死的测试**：阈值两侧该通过还是该拒绝，是读语料决定的。
  C 的阈值若变，Zig 侧必须跟着变，否则红；
* **语料本身防漂移**：`check-c.ps1` 重跑生成器并逐行比对。两个方向都验过——

逐位相同。留着它是因为某个超越函数在不同后端差 1 ulp 时，我宁愿看到一次容差内的通过，

## 30. math/interpolation：把分配器参数化落到实处（math 阶段完成）

§8.2 的第 1 条几乎就是针对这个模块写的：C 版有 34 处 `malloc`/`free`——六个要活过
`Init` 的系数数组，五个只在求解期间用的临时数组。移植用**两种形态**回答它：

* `Spline(n)`：结数 `n` 是 comptime 参数，所有数组都是值的字段，求解所需的临时数组放在
  `init` 的栈上、返回即消失。**全程没有分配器**——这比"把分配器传进去"更强，也正是
  嵌入式目标真正需要的形态。
* `Dyn`：结数只有运行期才知道时使用，分配器由调用者给；临时数组在 `init` 返回前释放，
  所以调用者既不可能把它和系数数组搞混，也不可能漏掉它。

**系数数组按 C 真正写入的范围定长**。C 版用 `n` 个元素分配 `a`/`b`/`d`，却从不写
`a[n-1]`、`b[n-1]`、`d[n-1]`——`Evaluate` 到不了那里，最后一个区间在 `n-2` 结束——
于是那三个槽是**未初始化内存**。这里 `a`/`b`/`d` 是 `n-1`（一个区间一个），`c` 是 `n`
（回代要读 `c[i+1]`）。"未初始化"这个问题因此不存在，语料也只打印 C 真正填过的范围。

**四条变异探针**：`linear` 的阈值改成 0 → 3 个红（退化用例直接除以 1e-7）；`evaluate`
去掉区间外的钳位 → 3 个红；求解器里 `b` 的符号写反 → 5 个红；**删掉 `Dyn` 里一个
`defer allocator.free(z)` → 1 个红**。最后这条值得单独说："没有泄漏"不是声称的，而是
`std.testing.allocator` 在测试里断言的——删掉一个 `free` 立刻变成失败，而不是等到某天
内存耗尽。

**除语料之外的独立断言**：样条必须穿过自己的结点；结点共线时样条**精确等于那条直线**
（曲率系数全为 0）；`Dyn` 与 `Spline(n)` 在同一输入上逐点相同，所以"一个求解器两种外壳"
是被检查的事实而不是设计意图；贝塞尔曲线从 `p0` 出发、在 `p3` 结束。

`math` 阶段收尾：**31 个算法测试**，全部与修好的 C 版本逐值对照，其中每个模块都保留了
不依赖对照物的断言。

## 31. 语料新鲜度检查在 Linux 上抓到了宿主差异（已修）

推完 quaternion 与 interpolation 之后，CI 连续两次红。本地 `zig build ci` 与
`tools/check-c.ps1` 都是绿的，所以这是**只在 runner 上出现**的失败——正是最容易
被"我本地是好的"糊弄过去的那一类。日志给出的差异只有一行：

```text
line 90: committed 'quat_euler_roundtrip 0.300000042 -0.400000036 1.10000002'
         fresh     'quat_euler_roundtrip 0.300000042 -0.400000036 1.10000014'
```

**原因是真的，而且不是我的移植错**：C 库自己的结果在不同 libm 上不是逐位相同的。
`atan2f`/`asinf` 在 MSYS2/ucrt 与 glibc 上差 1 ulp，而我的语料新鲜度检查是**逐字比对**
文本，于是把 1 ulp 判成了漂移。

这里要更正一条更早的记录。§23 记的是"尺寸实测与宿主无关"——**那条仍然成立**，因为我验的是
Zig 编出来的目标文件（纯算术，逐字节相同）。但那条结论**不能推广到 libm 的结果**：
超越函数在不同实现之间本来就允许差最后一位。同一份仓库里，一类测量是宿主无关的，
另一类不是；把前者当证据去推后者，是这次红build 的根因。

**修法**：把语料新鲜度检查从"逐字比对"改成"数值比对"，用与 Zig 侧**同一把尺子**
（1e-6 相对容差）。同时保留严格性：

| 情况 | 结果 |
|---|---|
| 用例被重命名 / 新增 / 删除 | **失败**（名字与个数要求完全一致） |
| 某个值移动超过容差 | **失败**，并报出用例名、两个值与相对差 |
| 只在最后一位差 1 ulp（宿主/libm 差异） | 通过，并把**最大相对差**打印出来 |
| 整份完全一致 | 打印 "identical to a fresh run" |

**三条探针**（改语料文件本身）：把 `vec2_dot -5` 改成 `-4`（20%）→ 失败；把
`spline_eval_between` 改名 → 失败；把 `quat_euler_roundtrip` 的末位改成 runner 上那个值
（1.1e-7）→ **按预期通过**。第三条是这次修复的目的，所以它必须被证明。

**验证是在 Linux 上做的**，不是靠本地绿：容器里（Ubuntu 22.04 + gcc 11.4 + glibc）跑真实
脚本，通过，并打印

```text
corpus  the committed C answers match a fresh run (largest relative difference
        1.1E-007 at quat_euler_roundtrip[2]: 1.10000002 vs 1.10000014)
```

一句"两边一致"从此带上了数量级。这也说明 Zig 测试那侧的 1e-6 容差从一开始就是对的——
它在 runner 上从来没红过，红的只是那条**比 Zig 测试更严格**的文本检查。

## 32. filter 阶段开始：三个递归标量滤波器（filter 进行中）

`math` 之后按 §8.3 的顺序进入 `filter`（5 个头文件、822 行）。本轮做前三个——
`low_pass`（含 EWMA）、`high_pass`（含 DC 阻断）、`complementary`——它们的形状相同：
一个状态结构体、一个 alpha、一个 `update`。

**有状态的东西让语料的形状变了。** 数学模块一个用例是"一组输入 → 一组输出"，
滤波器是"一串输入 → 一串输出"，所以每次完整运行是一条用例：
`lowpass_run 10.5 11.125 11.09375 12.8203125 11.1152344`。读语料就能看出行为，
而不是靠测试里的循环去猜。

**这套移植改的是"错误怎么表达"，不是数值。** C 版在每个入口都做空指针检查，
在时间常数非法时**静默什么都不做**——调用者无法区分"我设成功了"和"我设失败了"。
Zig 版把它变成 `error.InvalidTimeConstant`，而 C 的那份结果仍然记在语料里
（`*_alpha_invalid_tc_unchanged`），所以"这里行为不同"是被记录的差异，不是顺手改掉的。

**两处只能靠读代码发现的差异，都由语料钉住了**：

* 低通和高通**从同一个时间常数推出 alpha 的方向相反**：低通用
  `dt/(tc+dt)`，高通用 `tc/(tc+dt)`。同样的 0.5 与 0.1，一个得 0.167、一个得 0.833。
  这写进了 `filter/common.zig`，让"两者不同"在一个地方可见。
* 低通/EWMA 在未初始化时的第一次 `update` **返回输入**，高通/DC 阻断返回 **0**。
  这不是笔误：高通在看到一个样本之前没有直流可报告。四条用例分别记录了这四种行为。

**四条变异探针**：低通把两个增益对调 → 4 个测试红；高通把时间常数的方向改成低通那种
→ 3 个红；DC 阻断不减去均值 → 3 个红；互补滤波丢掉俯仰角的负号 → 3 个红。

**一条我自己写错、被测试抓出来的断言**：我断言 `alpha = 1` 的高通在输入持平时输出归零，
实际是**保持**——`alpha = 1` 时它退化成"变化量累加器"。断言改成钉住真实行为（阶跃向上、
持平保持、阶跃回落），这条性质现在也被记下来了。测试写错和移植写错一样常见，
所以两者都要能让彼此失败。

`filter` 还剩 `kalman`（1D 卡尔曼；头文件里那个 4 维类型**没有任何实现**，是"等数学模块"
留下的空壳，本轮按迁移原则不替它实现，只记录）与 `median`（1D 中值 + 图像中值，
唯一带分配的滤波器）。

## 33. filter 阶段收尾：kalman 与 median（filter 完成）

**`kalman`：一个只有类型、没有函数的 4 维滤波器。** 头文件里 `BreezeKalmanFilterND`
有 `dim`/`meas_dim` 和六个 4×4 矩阵，注释写着"实现需要矩阵运算支持，将在后续的数学工具
模块中添加"——而矩阵模块现在有了。但**移植不替它实现**：它没有任何行为可供对照，
写出来是加功能，不是迁移。语料里记了它的体积（`kalman_nd_layout 408 4`），
所以这个缺口是**可见的**，不是被忘掉的。要补的话，那是一次单独的、带自己测试的变更。

1D 那个没有做任何值域检查，移植也照旧不检查：`r` 给一个荒谬的值就会得到荒谬的结果，
替它发明一套策略属于设计变更。语料里跑了三条轨迹（默认、改 `a`、改 `h`），
另加两条不依赖语料的性质——过程噪声大时紧跟测量值、测量噪声大时几乎不动，
以及增益恒在 (0, 1]、协方差恒正。

**`median`：整个 filter 阶段唯一的一处分配。**

* 1D 中值在 C 里要调用者传两个缓冲区（`buffer` 与 `sorted`）。Zig 版把两个数组做成值的
  字段，于是窗口大小是 comptime 参数、**没有第二个指针需要与第一个保持同步**，
  而 C 里"缓冲区是 NULL 就原样返回输入"这个状态在这里根本无法表达。
* 图像版本的 `malloc` 换成**调用者提供的 scratch 切片**——"不强迫使用堆"的最直接形式；
  想要旧行为的人自己分配 `k*k` 字节传进来即可。`scratch` 太小、尺寸非法都会报错，
  而 C 是静默返回。
* 语料把三个图像用例钉住了，其中一个值得单说：`median_image_stride` 用 0xEE 预填充
  目标缓冲区，于是**哪些字节属于这个函数**一目了然——填充列保持 0xEE 不变。
  这是"stride 大于宽度"这类真实细节，靠读代码容易看漏，靠数据不会。
* 偶数核会**被进位成奇数**（k=4 → 5），语料里 k=3 与 k=4 的输出不同，
  所以这条不只是形式上的：进位是**可观测的**。

**四条变异探针**：卡尔曼增益分母写成 `q` 而不是 `r` → 4 个测试红；中值取中间下标时偏一位
→ 1 个红；图像边界不钳位 → 3 个红；去掉 scratch 大小检查 → 1 个红
（那个测试同时验证了"k=4 需要 25 字节而不是 16"，即进位后的尺寸要求）。

filter 五个模块到此完成：**51 个算法测试**（math 31 + filter 20）。下一阶段是
`control`（10 个头文件、2375 行、含 `platform/` 下 6 个平台控制器），是目前最大的一块。

## 34. control 阶段开始：pid 与 state_feedback（control 进行中）

**「微分滤波」不滤波。** `pid_controller.h` 的位置式里，被 alpha 混合的两项在解析上是
同一个量：

```text
derivative           = (measurement - prev_measurement) / dt
(prev_error - error) = (measurement - prev_measurement) / dt      [设定值不变时]
```

所以 `alpha * derivative + (1 - alpha) * derivative` 是**一个值与自己的凸组合**。
语料把边界也划清了：三条不同 alpha 的运行（0 / 0.7 / 1）**只在第一个样本**上不同——
因为 `prev_error` 的初值是 0、而首次误差不是——之后逐位一致，剩下的差别只是混合的舍入
（alpha=0.1 的运行在第 5、6 个样本上差最后一位，0.7 与 1 则完全相同）。
`SetDerivativeFilter` 因此只改变第一个输出和最后一位。移植**照原样计算**并把这条性质
写成断言（首样本不同、其余逐位相同），而不是"顺手清理"——清理之后就不再等于它要替代的
那份实现了。增量式里 alpha 根本没被读过。

**`state_feedback` 里那个没人读的模型。** `BreezeLQRController_Init` 会存下
`A`/`B`/`Q`/`R`、`max_iterations`、`convergence_tol`，注释写着"完整的 LQR 求解器需要
矩阵运算支持，将在数学工具模块中实现"——而矩阵模块现在有了，它从没被写出来。移植做了
两件事：

* **模型字段消失**。它们被存进去、没有任何东西读；留着它们会让调用者以为自己传的模型
  算出了增益。去掉之后那种误解**无法编译**。语料仍记下它们（`lqr_a00_stored`、
  `lqr_max_iterations_stored`…），缺口是可见的。
* **两个类型合成一个**。两个 C 的 `Compute` 是同样的代码作用在同样的字段上，
  于是语料同时记录两者，而这里一份实现同时对上两者。

要写 Riccati 求解器，那是一次带自己测试的功能变更，不是迁移：没有可供对照的 C 行为。

另外，C 的状态维度是运行期值、由固定数组限死为 4；Zig 版做成 comptime 参数且无上限，
因为那个上限是**存储方式的产物**，不是控制律的规则。

**四条变异探针**：位置式去掉微分项负号 → 5 个测试红；去掉抗积分饱和钳位 → 3 个红；
增量式改成走位置式 → 3 个红；状态反馈的求和符号反过来 → 5 个红。

control 还剩 `fuzzy`（394 行，是 control 里唯一带分配的：4 处 `malloc`）、
`adaptive`（287 行），以及 `platform/` 下 6 个平台控制器。

## 35. control：平台 I/O 面做成 comptime 参数（差速驱动完成）

**函数指针换成类型参数。** C 把 `BreezeMotorControlFunc` / `BreezeEncoderFunc` 存在控制器
结构体里，于是每次读写外设都过一次指针——这也是为什么每个 C 入口都要查空指针。
Zig 侧写成 `DifferentialDrive(Io)`，`Io` 是 comptime 类型参数，与内核 HAL、示例应用的
模块 I/O 面同一形状。两条后果，都是有意选的：

* 缺函数在**编译期**报出来，而且点名缺哪个、签名是什么：
  `platform 'X' must declare readEncoder(encoder_id: i32, reset: bool) f32`。
* 控制器不能在运行期换成另一个平台——而这正是它从未用过的灵活性：C 的例子在 `Init`
  里传一次平台，之后再没换过。

**一个数字上的细节**：C 用的是字面量 `2 * 3.14159 * radius`，不是 `M_PI`。若"顺手"
改成 `std.math.pi`，结果在第五位小数上就变了（18.84954 → 18.84956），语料会红。
这类事没有语料就只能靠人眼，而人眼不看第五位。

**语料污染与"每条用例从自身设置复现"。** 第一版生成器里，那块"调参后运行"接在
"默认参数运行"之后、复用同一个控制器，于是它继承了前一次的三拍 PID 历史，C 给出
`-0.443629086`——一个**任何全新控制器都复现不出的值**，移植自然对不上（我的移植给出
`-0.840871`）。修法不是让 Zig 测试去模拟那份残留，而是让生成器用一个**全新控制器**，
于是 C 的值变成 `-0.840870976`，与移植一致。语料里的每条用例都应当能独立复现；
做不到的用例，是在邀请后来者猜。

**两条探针先后暴露的是 fake 的记录方式，而不是被测代码**，但结论一样——探针不红等于没测：

| 问题 | 表象 | 修法 |
|---|---|---|
| `g_motor_calls` 只在循环外重置一次 | 三次运行的电机指令**完全相同**（记的是第一次重复三遍） | 每拍重置；数据一眼可疑，正是"看数据"抓到的 |
| fake 忽略 `reset` 标志 | 去掉 `reset` 的变异**不红** | 记录 `reset`；记录"最后一次"**仍然不红**（只改了左轮，右轮覆盖了它）→ 改成记录**每一次**并断言全部为真，两个方向的变异各红 3 个测试 |

第二条特别值得记：**用一个末值代表一串调用**，会把"其中一次不同"完全掩盖。
这和 §31 那条"用一个文本比对代表数值一致性"是同一类错误——度量方式本身把要发现的东西
藏了起来。

**变异探针**：`3.14159` 换成 `π` → 4 个红；左右轮目标互换 → 4 个红；不发电机指令 → 4 个红；
两个编码器读的 `reset` 各改一次 → 各 3 个红；`Io` 少一个函数 → 编译失败并点名。

## 36. control：全向平台，以及一处真的控制律缺陷

**旋转项对所有轮子相同，那不是旋转。** C 的逆运动学是

```text
wheel_targets[i] = vx·cos(θᵢ) + vy·sin(θᵢ) + wheel_distance·ω
```

最后一项对每个轮子**都一样**。可轮子位于不同角度，纯旋转时它们的切向速度方向不同——
给所有轮子加同一个常数，得到的是"沿平均轮方向的平移"，不是"绕中心的转动"。
这不是文档与代码不符，而是控制律本身错了。**移植仍然照抄**：它的职责是等于被替代的
实现，不是替它做设计决定；修它是另一次变更。为了让这条缺陷**可断言**，
我把逆运动学从 `Update` 里提出来变成纯函数 `wheelTargets(vx, vy, ω)`
（C 里它是内联的，测试够不着），测试直接断言"纯旋转下三个目标完全相同"——
把行为钉住，而不是在注释里描述它。

顺带值得记的是为什么这条要断言在**目标**而不是**指令**上：三个轮子的编码器读数不同，
所以它们的 PID 输出本来就不同；端到端命令相等只能说明饱和，说明不了目标相等。

**又一条探针发现的空白。** "每轮都不得超过最大线速度就整体重标定"这段，语料里
**从未被触发**——正常运行下原始目标最大只有 0.32，远小于上限 1.0，于是删掉这段代码
所有测试照样绿。补的用例是"满线速度 + 满角速度"（原始目标 1.3 > 1.0），
并从 PID 的 setpoint 把重标定后的目标读回来（那是 `Update` 存放目标的地方）。
补上之后，删掉重标定的变异红 3 个测试。

这是本项目里第三次"探针发现某条路径根本没被测到"（前两次见 §32、§35）。
它们的共同点：**代码在，但没有一条用例走到它**。覆盖率数字不会告诉你这件事，
只有"故意改坏它"会。

**fake 也跟着长了一维**：从两个电机槽扩到四个，编码器序列按 **encoder id**（1..4）
索引、按**第几拍**取值，由用例在每拍开始前设置。原来那版靠"读到非 1 号就自增"来推进，
在 3 轮与 4 轮平台上会推错次数。改完之后差速那几条语料**逐字未变**（`git diff` 为空），
所以这次重构是保行为的——这一点是查过的，不是推断的。

**变异探针**：`3.14159` 换成 `π` → 3 个红；径向钳位换成逐分量 → 3 个红；
旋转项符号反 → 4 个红；删掉重标定 → 3 个红（补用例之前是 0 个）。

## 29. math/quaternion（已完成）

三处 `int` 返回值变成类型：`Normalize`、`Inverse` 用 `error.Degenerate`，`ToEulerZYX`
的三个出参合成一个 `EulerZYX` 值。指针检查与 out-param 的处置同 §27，这一节只记
**这个模块特有的东西**。

**两处"照抄而不改进"**，因为迁移要对齐的是实现，不是更好的想法：

* `fromAxisAngle` 对退化轴**返回单位四元数**。"绕零轴旋转任意角"是有答案的，C 版给了
  这个答案；想区分的调用者可以自己先归一化再判断。
* **两个 1e-6 阈值量的不是同一个东西**：`Normalize` 拿它比**模**，`Inverse` 拿它比
  **模的平方**。模为 1e-4 的四元数，前者接受、后者拒绝。语料里两边各有一条用例
  （`quat_normalize_boundary_ok 1` 与 `quat_inverse_boundary_ok 0`）把这件事钉死——
  这不是一条"注释与代码不符"的发现，而是一条**可执行的不对称**，谁想改都必须先改语料。

三角函数从这一模块开始进来（`sinf`/`cosf`/`asinf`/`atan2f`/`acosf`），所以这里也是
容差真正起作用的地方：两边的 libm 实现可能差 1 ulp。今天仍然逐位相同，但这是第一个
"万一不同也不该报错"的模块——容差存在的理由在 §27 里写的是"防备将来"，这里是那个将来
最可能出现的位置。

**万向节锁**单独测：pitch = π/2 时 C 版把 pitch 钉在 ±π/2、roll 按约定置 0、yaw 换一个
公式。语料存下了那个分支的结果（`quat_euler_gimbal 0 1.57079637 -0.962284148`），
所以"这段特殊处理还在"是被检查的。

**四条变异探针**：去掉负点积翻转 → 3 个测试红；把 `Inverse` 的阈值改成比模而非模平方 →
3 个红；去掉万向节锁分支 → 3 个红；`fromAxisAngle` 不归一化轴 → 3 个红。

除语料比对外，这个模块也留了**不依赖语料**的断言：单位四元数的逆等于其共轭且乘积为单位、
绕 Z 轴 90° 把 +X 映到 +Y、旋转保长、slerp 到一半等于绕同一轴转一半角。对照物能证明
"一致"，不能证明"正确"，两者都要有。

## 28. math/matrix（已完成）

`matrix.h` 和向量不是一类东西：它把形状放在**运行期**（`float data[4][4]` 加
`rows`/`cols`），于是每个函数开头都要检查形状，失败就返回 `0`。Zig 里形状是类型的
comptime 参数，四类运行期失败因此整体变成编译错误——加 2×3 与 3×2、内维不匹配、
对非方阵求行列式，以及 **4×4 的行列式与求逆**。最后一条尤其值得说明：C 版对它返回
`0.0f`，注释写着"4x4 及更大……这里不实现"，移植版改为**拒绝编译**。补上 4×4 是一件
有意的功能变更，不该藏在"迁移"里顺手做掉；等真的需要时再单独做，并给它自己的测试。

两处差异单独记，因为它们是**有意丢掉**的东西，不是漏掉的：

* **形状之外没有存储了**。C 的 `Init` 只把使用区域清零，4×4 数组的其余部分原样保留；
  `Mat(2, 3)` 没有"其余部分"。语料里留了一条记录 C 存储形态的用例
  （`matrix_layout 72 4` 对 `matrix_data_bytes 64`），读者有权知道这个差异。
* **原地操作是安全的**。C 的 `Multiply`/`Transpose` 特意用临时量以支持 `result` 与
  输入同址——但 **`Inverse` 没有**：`Inverse2x2(&m, &m)` 先写 `[0][0]`，而 `[1][1]`
  还要读它，于是把 `m` 写坏。按值传递让两种写法都安全，并且加了一条测试：
  把矩阵乘以它自己的逆，期望单位阵。

**四条变异探针**（先弄坏，确认会红）：内维下标写反 → 语料比对报 `ValueMismatch`
（连带 4 个测试红）；行列式符号写反 → 5 个测试红；奇异阈值从 `1e-6` 改成 `0` →
奇异用例报 `TestExpectedError`；转置忘了交换下标 → **编译器**直接拒绝
（comptime 展开后下标越界），比测试失败更早一步。

那条"逆真的是逆"的测试是**故意独立于语料**的：如果两边错得一样，逐值比对会放过，
而它不会。对照物能证明"一致"，不能证明"正确"——两个都要有。
